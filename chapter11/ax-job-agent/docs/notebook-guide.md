# AX Job Agent Notebook 작성 가이드

## 1. 문서 목적

이 문서는 `ax_job_pipeline.ipynb`를 일관된 형식으로 작성하기 위한 규칙을 정의한다.

`project-guide.md`가 **무엇을 수행해야 하는지**를 정의하는 프로젝트 실습 지침이라면, 이 문서는 **그 작업을 노트북에 어떻게 기록할 것인지**를 정의한다.

노트북은 단순한 코드 실행 공간이 아니라 다음 내용을 확인할 수 있는 실습 기록으로 작성한다.

* 무엇을 하려고 했는가?
* 어떤 코드를 작성했는가?
* 실제로 어떤 결과가 나왔는가?
* 그 결과를 어떻게 해석했는가?
* 해당 STEP의 완료 조건을 충족했는가?

---

## 2. 기본 작성 원칙

각 STEP은 다음 순서로 작성한다.

```text
작업계획
    ↓
실제 코드
    ↓
실행결과/분석
```

노트북에서는 다음과 같은 셀 구성을 기본으로 한다.

```text
[Markdown] STEP 제목 및 작업계획

[Code] 실제 코드

[Markdown] 실행결과/분석
```

필요한 경우 하나의 STEP 안에서 여러 개의 코드셀을 사용할 수 있다.

이 경우에도 각 코드셀의 목적이 작업계획과 연결되도록 작성한다.

---

## 3. STEP 제목 작성 규칙

각 STEP의 시작에는 `project-guide.md`의 STEP 번호와 제목을 그대로 사용한다.

예:

```markdown
# STEP 03. 채용공고 페이지 접근 테스트
```

STEP 제목은 임의로 변경하지 않는다.

프로젝트 가이드와 노트북의 STEP 번호 및 제목을 동일하게 유지하여 두 문서를 쉽게 비교할 수 있도록 한다.

---

## 4. 작업계획 작성 규칙

각 STEP의 첫 번째 내용은 작업계획을 작성한다.

기본 형식:

```markdown
## 1. 작업계획

이번 단계에서는 무엇을 확인하거나 구현하는지 설명한다.

### 목표

- 이번 단계에서 확인할 내용

### 작업 내용

1. 첫 번째 작업
2. 두 번째 작업
3. 세 번째 작업

### 완료 조건

- 프로젝트 가이드에서 요구하는 완료 조건
```

작업계획에서는 아직 실행하지 않은 결과를 사실처럼 작성하지 않는다.

예를 들어 다음과 같이 작성하지 않는다.

```text
요청 결과는 200이 나올 것이다.
```

대신 다음과 같이 작성한다.

```text
HTTP 요청을 보내 상태 코드를 확인한다.
```

즉, **계획과 결과를 구분한다.**

---

## 5. 실제 코드 작성 규칙

작업계획 다음에는 실제 Python 코드를 작성한다.

코드는 반드시 실행 가능한 상태로 작성한다.

예:

```python
import requests

url = "채용공고 URL"

response = requests.get(
    url,
    headers={
        "User-Agent": "Mozilla/5.0"
    },
    timeout=10,
)

print("status:", response.status_code)
print("content-type:", response.headers.get("Content-Type"))
print("response length:", len(response.text))
```

### 코드 작성 원칙

* 작업계획에 필요한 코드만 작성한다.
* 사용하지 않는 코드를 불필요하게 추가하지 않는다.
* 코드 실행 결과를 임의로 작성하지 않는다.
* 가능한 한 한 셀에서 하나의 작업 목적을 명확하게 한다.
* 오류가 발생하면 오류를 숨기지 않는다.
* 오류가 발생한 경우 원인을 확인하고 수정한 뒤 다시 실행한다.

---

## 6. 실행결과/분석 작성 규칙

코드를 실행한 후 실제 결과를 확인하고 Markdown 셀에 결과와 분석을 작성한다.

기본 형식:

```markdown
## 3. 실행결과/분석

### 실행결과

- HTTP 상태 코드: 200
- Content-Type: text/html
- 응답 길이: 실제 실행 결과
- HTML 응답을 정상적으로 확인함

### 분석

HTTP 요청이 정상적으로 처리되었으며,
응답 HTML에서 채용공고 정보를 확인할 수 있었다.

따라서 다음 단계의 데이터 수집에 사용할 수 있는지
추가로 검토한다.

### 완료 여부

- [x] HTTP 요청 확인
- [x] 응답 상태 확인
- [x] HTML 구조 확인
- [x] 채용정보 존재 여부 확인
```

실행결과는 **실제 실행된 결과를 기준으로 작성한다.**

---

## 7. 실행결과와 분석의 구분

실행결과와 분석을 구분한다.

### 실행결과

코드를 실행해서 실제로 확인한 사실을 기록한다.

예:

```text
HTTP 상태 코드: 200
응답 길이: 184532
Content-Type: text/html
```

### 분석

실행결과가 의미하는 바를 설명한다.

예:

```text
HTTP 요청이 정상적으로 처리되었다.
응답이 HTML 형식이므로 페이지 구조를 분석하여
채용공고 정보를 추출할 수 있는지 확인할 수 있다.
```

분석에서는 실행결과에서 확인할 수 없는 내용을 임의로 추측하지 않는다.

## 8. 완료 조건 확인

각 STEP의 마지막에는 해당 STEP의 완료 여부를 확인한다.

기본 형식:

```markdown
### 완료 여부

- [x] 완료 조건 1
- [x] 완료 조건 2
- [x] 완료 조건 3
```

완료하지 못한 항목이 있다면 `[ ]`로 남긴다.

예:

```markdown
### 완료 여부

- [x] HTTP 상태 코드 확인
- [x] Content-Type 확인
- [x] HTML 구조 확인
- [ ] 채용공고 정보 추출 가능 여부 확인
```

모든 완료 조건을 확인한 후 다음 STEP으로 이동한다.

## 9. 오류 처리 원칙

코드 실행 중 오류가 발생하면 오류를 숨기지 않는다.

다음 순서로 처리한다.

```text
오류 발생
    ↓
오류 메시지 확인
    ↓
원인 분석
    ↓
코드 수정
    ↓
다시 실행
    ↓
결과 확인
```

필요한 경우 오류 내용을 Markdown으로 기록한다.

예:

```markdown
### 오류 및 해결

첫 번째 실행에서 `ConnectionError`가 발생하였다.

요청 대상 서버에 연결되지 않았기 때문에 발생한 오류로 판단하였다.
요청 URL과 네트워크 상태를 확인한 후 다시 실행하였다.

두 번째 실행에서는 정상적으로 응답을 확인하였다.
```

오류가 발생했다는 사실 자체를 숨기기보다는,
**어떤 문제를 확인하고 어떻게 해결했는지**를 기록한다.

## 10. 데이터와 결과의 임의 생성 금지

실제 프로젝트에서 수집하지 않은 데이터를 실제 결과처럼 작성하지 않는다.

특히 다음을 임의로 만들지 않는다.

* 채용공고
* 회사명
* 채용공고 URL
* HTTP 응답 결과
* DataFrame 결과
* Gemini 분석 결과
* Slack 전송 결과
* Gmail 전송 결과

실제 데이터가 필요한 경우에는 실제 수집 데이터 또는 프로젝트에서 제공한 샘플 데이터를 사용한다.

## 11. STEP별 독립성

각 STEP은 이전 STEP의 결과를 활용할 수 있지만,
현재 STEP에서 무엇을 수행하는지 명확하게 구분한다.

예:

```text
STEP 03
채용공고 페이지 접근 테스트

STEP 04
소량 데이터 수집

STEP 05
DataFrame 생성
```

STEP 03에서 수집 자체를 대규모로 수행하지 않는다.

각 STEP의 목적과 완료 조건을 기준으로 필요한 작업만 수행한다.

## 13. 코드 실행 결과의 재현성

가능하면 노트북을 처음부터 순서대로 실행해도 동일한 흐름으로 결과를 확인할 수 있도록 작성한다.

셀 간의 실행 순서에 지나치게 의존하지 않는다.

예를 들어 다음 셀에서 사용하는 `df`가 있다면,
해당 `df`가 어느 셀에서 생성되는지 명확해야 한다.

```python
df.head()
```

위 코드만 실행했을 때 `df`가 정의되지 않는 상황을 피한다.

## 14. 출력 결과 확인

중요한 결과는 단순히 출력하는 것으로 끝내지 않는다.

예:

```python
print(df.shape)
display(df.head())
display(df.isna().sum())
```

실행 후 Markdown에서 결과를 해석한다.

예:

```text
실행 결과 DataFrame은 10행으로 구성되었다.

초기 컬럼 9개가 생성되었으며,
`job_url`의 결측값은 확인되지 않았다.

따라서 현재 데이터는 다음 단계의 중복 및 결측값 점검에 사용할 수 있다.
```

## 15. 데이터 분석 결과 작성 원칙

분석 결과에서는 가능한 한 숫자와 실제 결과를 근거로 설명한다.

좋은 예:

```text
전체 10건의 채용공고 중 2건에서 동일한 job_url이 확인되었다.
따라서 중복 제거가 필요하다.
```

피해야 할 예:

```text
데이터가 상당히 많아서 중복 제거가 중요하다.
```

가능하면 다음과 같이 구체적으로 작성한다.

```text
전체 건수: 10건
중복 건수: 2건
중복 제거 후: 8건
```

## 16. 외부 API 사용 시 원칙

Gemini, Slack, Gmail 등의 외부 서비스는 실제 호출 결과를 기준으로 기록한다.

API 호출 전에는 작업계획에서 다음을 설명한다.

* 어떤 API를 사용하는가?
* 왜 사용하는가?
* 어떤 입력을 전달하는가?
* 어떤 결과를 기대하는가?

API 호출 후에는 실제 결과를 확인한다.

API 키나 비밀번호 등의 민감한 정보는 노트북에 직접 기록하지 않는다.

예:

```python
import os

api_key = os.getenv("GEMINI_API_KEY")
```

민감한 값 자체를 출력하지 않는다.

잘못된 예:

```python
print(api_key)
```

## 17. 환경변수 및 비밀정보 관리

다음 정보는 노트북에 직접 기록하지 않는다.

* API Key
* Password
* Token
* 개인 계정 인증정보
* GitHub Secret 값
* Slack Webhook URL 등 민감한 인증정보

필요한 경우 `.env`와 환경변수를 사용한다.

예:

```python
from dotenv import load_dotenv
import os

load_dotenv()

api_key = os.getenv("GEMINI_API_KEY")
```

`.env` 파일 자체는 Git에 커밋하지 않는다.

## 18. Markdown 작성 스타일

Markdown은 코드를 설명하기 위한 목적으로 사용한다.

가능하면 다음과 같이 작성한다.

```text
목표
→ 작업 방법
→ 실행 결과
→ 분석
→ 완료 여부
```

긴 설명을 불필요하게 반복하지 않는다.

중요한 값이나 결과는 표나 목록을 사용하여 읽기 쉽게 작성한다.

## 19. 코드 주석 작성 스타일

코드 주석은 코드 자체만 보고 이해하기 어려운 부분에 작성한다.

좋은 예:

```python
# 채용공고 URL을 기준으로 중복 여부를 확인한다.
df.duplicated(subset=["job_url"]).sum()
```

불필요한 예:

```python
# df를 출력한다
print(df)
```

코드 자체로 의미가 명확한 경우에는 주석을 과도하게 추가하지 않는다.

모든 항목을 확인한 후 다음 STEP으로 이동한다.

## 22. 핵심 원칙

이 노트북의 가장 중요한 원칙은 다음과 같다.

> **계획한 내용을 코드로 실행하고, 실제 실행 결과를 확인한 후 분석한다.**

즉,

```text
계획
 ↓
코드
 ↓
실행
 ↓
실제 결과
 ↓
분석
 ↓
완료 확인
```

의 흐름을 유지한다.

노트북은 코드 모음이 아니라 **AX Job Agent를 단계적으로 구현하고 검증한 실습 기록**이 되도록 작성한다.
